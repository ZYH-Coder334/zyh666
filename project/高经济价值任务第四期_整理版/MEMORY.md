## 1. 项目简介

### 这是什么

**涉密资质甲级**是本工作区内一个"AI 能力评测任务"（benchmark），目标是检验大语言模型在**复杂多表跨表合规审查**场景下的信息抽取、条件判定和跨表勾稽能力。

### 任务形式

模拟一家名叫"华信安通科技有限公司"的虚构企业，委托第三方审查顾问对其提交的涉密信息系统集成资质甲级申请材料进行合规性审查。候选模型需要：

- 读取 8 包 rar 格式的输入附件（内含多个 xlsx）
- 对照资质条件，对数据逐条审查
- 输出 8 包 rar 格式的审查答案
- 答案必须是 xlsx 格式，结论分三类：**符合 / 合规保留 / 不符合**
- 所有分类汇总必须闭合（总数 = 符合 + 合规保留 + 不符合）

### 设计约束

| 约束 | 说明 |
|---|---|
| 难度目标 | 千问 3.8 在 v5 上得分率 83%（39/47），v6 目标 **<50%** |
| 附件格式 | 8 输入 + 8 答案，格式为 **zip 压缩文件但扩展名必须是 .rar** |
| 无 AI 痕迹 | xlsx 的 docProps（app.xml / core.xml）必须伪装成真实 Excel 产物，不能带 openpyxl 指纹或 AI 版本标识 |
| 数据一致性 | 所有数据必须自洽，跨表勾稽必须闭合，答案生成脚本内部自检通过才能打包 |

### 各版本演进

| 版本 | 完成时间 | 核心变化 |
|---|---|---|
| v2 | 待确认 | 早期原型，单 xlsx 多 sheet |
| v3 | 待确认 | 拆分为 rar 格式，增加涉密批文 / 非密认定 |
| v4 | 待确认 | 增加社保基数对照表、关联方别名；仍有数据逻辑缺陷（姓名不匹配、时间矛盾、编号断号） |
| v5 | 待确认 | 修复 v4 数据缺陷，花名册 600 / 涉密 350 / 项目 240 |
| v6 | 2026-10-23（当前） | **数据翻倍**（花名册 1000 / 涉密 500 / 项目 400 / 设备 88 / 制度 40），**集成收入从 4 重判定增至 7 重**（新增全额发票、密级认定、归档状态），场所校验 6 维（新增公摊净面积、物理隔离、设备密级匹配、档案室三铁），职称 5 维（新增证书编号格式、发证机关权限），涉密人员培训有效期 1 年，28 项跨表勾稽 |

### v6 脚本内部架构

每个脚本都是**单文件、无函数复用**的独立 Python 脚本，风格统一：

- 用 `openpyxl.Workbook()` 直接创建工作簿
- `make_sheet(wb, name, headers, data, col_widths)` 辅助函数封装表头样式（深蓝底白字）
- 所有日期用 `date(2025, 9, 1)`（REF）作为基准日
- `gen_miji_v6_q.py`：先用 7 个大列表装数据，最后逐个 `make_sheet` 写入
- `gen_miji_v6_ans.py`：用 `openpyxl.load_workbook(... data_only=True)` 读题目 xlsx → 逐表遍历 → 构造答案行 → 写入答案 xlsx
- `split_miji_v6.py`：先拆 sheet → 然后覆盖 zip 内部的 `docProps/app.xml` 和 `docProps/core.xml`（伪装成 Microsoft Excel 16.0300）→ 改扩展名 .zip → .rar

## 6. 开发过程中踩过的坑和解决方案

### 坑 1：openpyxl 的指纹 / AI 痕迹

**现象**：直接用 openpyxl 保存的 xlsx，内部 `docProps/app.xml` 里有 `<Application>Microsoft Excel</Application>` 但也可能带 openpyxl 自身指纹；`docProps/core.xml` 的 creator/lastModifiedBy 可能是 "openpyxl" 或 AI 生成器标识。

**解决**：打包脚本 split_miji_v6.py 里用 zipfile 重新打包，覆盖两个关键 xml：

```python
APP_XML = (..., '<Application>Microsoft Excel</Application>', ...
           '<AppVersion>16.0300</AppVersion>', ...)

def core_xml(author, created, modified):
    return (..., f'<dc:creator>{author}</dc:creator>', ...
             f'<dcterms:created xsi:type="dcterms:W3CDTF">{created}</dcterms:created>')
```

作者字段伪造为 "综合管理部"、"合规咨询组" 等中文机构名。

### 坑 2：项目总数超量 / 计数不匹配

**现象**：v6 第一次跑 `gen_miji_v6_q.py` 报 AssertionError，项目数不是 400；集成收入计入数比预期少 30 多项。

**根因**：手写的循环数 `for i in range(164)` 等是硬编码，如果前面加/减了边界项，总数会飘；涉密批文名额限制成 55 份，但涉密系统集成项目有 87 个，导致 32 个涉密项目无批文被剔除。

**解决**：
- 调整小额计入项循环次数（164 → 159）以让总数回到 400
- 把批文从 "限额 55 份" 改为 **"覆盖所有涉密系统集成项目，排除 no_doc_pids（人为设置的 12 个无批文陷阱）"**
- 非密认定同理

### 坑 3：证书编号后缀逻辑写错

**现象**：v6 第一次答案生成，计算机类高级职称 cs_n=0、cs_valid=1。

**根因**：发证机关权限校验要求"正高证书末位须为 1、副高须为 2"，但写证书编号时所有 CS 职称都用 `f'Z2014{i:03d}1'`（全以 1 结尾），包括副高。导致所有副高的证书编号格式校验失败。

**解决**：在题目生成器里按正高/副高分别后缀：
```python
suffix = '1' if is_正高 else '2'
f'Z2014{i:03d}{suffix}'
```

### 坑 4：涉密人员培训过期过多

**现象**：v6 第一次答案生成，`c_train_exp`（培训已过期）达到 236 人，绝大部分"符合"类也被判定为过期。

**根因**：符合类人员的培训日期用 `dstr(2024, (i % 12) + 1, 25)`，而基准日是 2025-09-01，一年有效期即 2024-09-01。很多人培训日期在 2024-08-25 之前，恰好过期。

**解决**：用 2024-09-01 之后的月份生成培训日期：
```python
train_m = 9 + (i % 12)
train_y = 2024 if train_m <= 12 else 2025
```

### 坑 5：关联方别名识别

**现象**：最开始项目甲方只用了 `RELATED` 列表中的原名，模型根本不需要查"曾用名"列就能识别关联交易。

**解决**：前 5 个关联方项目故意把甲方换成别名形式：
```python
real_rel = RELATED[i % len(RELATED)]
client_name = RELATED_ALIASES.get(real_rel, real_rel)
```
模型必须先读关联方名单的"曾用名/别名"列，构造完整集合（原名 ∪ 别名），才能正确识别。

### 坑 6：集成收入 7 重判定漏掉发票全额条件

**现象**：v5 的收入确认只要求"已开票"，模型直接用 `发票状态 == '已开具'` 就能全部识别，千问 3.8 这里得满分。

**解决**：v6 新增"发票类型"字段（全额 / 部分开票），并设置 8 个"部分开票"陷阱项目。模型必须检查 `发票类型 == '全额'`，部分开票即使金额足够也不计入。

### 坑 7：证书编号格式陷阱 vs 答案生成器校验不匹配

**现象**：设置了证书编号格式陷阱（1 人 G 开头、1 人区级局发正高），但答案生成器一开始只校验专业归属，导致陷阱形同虚设。

**解决**：v6 高级职称审查从 1 维扩展到 5 维：①专业归属 ②证书编号 Z 开头 ③正高末位=1 / 副高末位=2 ④发证机关权限（正高须省部级）⑤证书状态有效。

### 坑 8：split 脚本的 docProps 覆盖顺序

**现象**：早期 split 脚本直接 zipfile 覆盖，但新写入顺序不固定，解压后 xml 解析顺序偶尔异常，导致 xlsx 能打开但样式丢失。

**解决**：覆盖时保持与原包相同的压缩方式（zipfile.ZIP_DEFLATED），且**只改 docProps/app.xml 和 docProps/core.xml 两个文件**，其他文件字节不变。

## 7. 硬性约定

### 文件命名

| 约定 | 示例 |
|---|---|
| 题目生成器 | `gen_miji_v6_q.py`（任务缩写 + 版本 + q 表示 question） |
| 答案生成器 | `gen_miji_v6_ans.py`（ans 表示 answer） |
| 拆分脚本 | `split_miji_v6.py` |
| 题目源文件 | `涉密资质甲级_v6_题目.xlsx` |
| 答案源文件 | `涉密资质甲级_v6_标准答案.xlsx` |
| 最终附件 | `涉密资质甲级_附件/输入附件/01企业证照与股权结构.rar` |
| 版本迭代 | **v2 → v3 → v4 → v5 → v6**，不跳版本 |

### 代码风格

- 所有生成器都是**单文件独立脚本**，**没有**跨任务 import（每个任务自包含）
- 用 `openpyxl.Workbook()` + `make_sheet()` 辅助函数写 xlsx，**不用 pandas**（pandas 有额外的 workbook metadata 痕迹）
- 日期统一用 `datetime.date(2025, 9, 1)` 作基准日（REF），所有边界计算从这里推
- 生成器里用大列表装数据（如 `roster = []`, `projects = []`），最后统一写入 xlsx
- 答案生成器里先 `load_workbook(data_only=True)` 读题目 xlsx，**再**逐表遍历生成答案

### 附件格式

- **扩展名固定为 .rar**，但实际内容是 zip（ZIP_DEFLATED 压缩）
- 输入附件和标准答案**一一对应**，8 个输入包配 8 个答案包
- rar 内部只能是 xlsx 文件，不能有其他格式（避免模型被非结构化内容干扰）
- 每个 rar 包名以两位数开头（01、02 ... 08），按阅读顺序编号

### docProps 伪装（必须做）

每个 rar 包里的每个 xlsx，打包时都要覆盖两个 xml：

| 文件 | 伪装内容 |
|---|---|
| docProps/app.xml | `<Application>Microsoft Excel</Application>`，`<AppVersion>16.0300</AppVersion>`，`<Company>华信安通科技有限公司</Company>` |
| docProps/core.xml | `<dc:creator>综合管理部</dc:creator>`，`<dcterms:created>` 和 `<dcterms:modified>` 设为虚构的 UTC 时间戳（如 2025-08-18T02:15:00Z） |

### 三分类约定

所有审查结论列只能取三个值：

| 值 | 含义 |
|---|---|
| **符合** | 条件满足，计入有效数 |
| **合规保留** | 本身不违规但不计入符合条件（如非涉密岗位的涉密人员、非计算机类职称、非涉密场所） |
| **不符合** | 条件不满足，须整改 |

每个审查维度的汇总必须闭合：`总数 = 符合 + 合规保留 + 不符合`

### 数据一致性红线

- 花名册人数 = 社保记录数（同一批人）
- 项目数 = 发票数（每个项目必有一张发票）
- 涉密批文项目 ⊆ 项目清单（不能出现项目清单外的项目号）
- 非密认定项目 ⊆ 项目清单
- 高级职称 ⊆ 花名册（不能有不在花名册里的人）
- 涉密人员 ⊆ 花名册（同上）
- 勾稽自检表的所有"勾稽项"列**必须**能在前述数据中找到对应
